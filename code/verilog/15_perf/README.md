# 第 15 章 性能计数器代码

## 文件

- `perf_counter.v`：性能计数器。累计周期数、提交数、四类停顿次数，并给出当前瓶颈编码和 IPC 的分子分母。
- `tb_perf.v`：自测程序，21 项检查全过。

## 计数器记什么

第 1 章算 CPI 时用的是一张手工账本。这里把它做成电路，每次时钟沿累加。

| 计数器 | 含义 | 对应第 1 章账本里的 |
|---|---|---|
| `cycle_o` | 累计周期数 | 分母，理想执行加各类停顿 |
| `commit_o` | 累计提交数 | 分子，真正退休的指令 |
| `front_stall_o` | 前端断粮的周期数 | 供指不足 |
| `issue_stall_o` | 发射口没货或执行端口不够 | 结构冒险在乱序核里的新形态 |
| `lsq_stall_o` | 访存队列满或等地址 | 访存 stalls |
| `recover_o` | 重定向与冲刷的周期数 | 控制冒险的代价 |

IPC 没有在硬件里做除法，只输出分子 `ipc_num_o` 和分母 `ipc_den_o`，交给上层软件算。定点除法会白丢精度，而且软件算起来不花钱。

## 接口怎么读

输入只有两类。一类是提交口每拍给的数 `commit_i`，表示这一拍提交了几条 uop。另一类是四个停顿事件信号，分别来自前端、发射、访存队列和恢复控制。

输出除了各个累计值，还有两个组合信号。

| 信号 | 含义 |
|---|---|
| `stall_any_o` | 本拍有没有停顿事件 |
| `bottleneck_o` | 当前最该治哪一块：0 前端、1 发射、2 访存、3 恢复 |

一拍里多个事件同时成立很常见，比如分支冲刷时前端也在断粮。`bottleneck_o` 按影响面取一个，恢复最重、前端最轻。这个优先级跟 Digital 电路 `15_bottleneck.dig` 里的判据完全对应。

## 四个关键落点

1. **周期和提交分开数**。周期每拍加一，提交按本拍实际条数加。IPC 是两者相除，不是拍脑袋估的。
2. **停顿按事件数，不按空气泡数**。同一个周期可能同时被记为前端断粮和恢复冲刷，两个计数器都会加一。这是为了让每类原因的账都记全，代价是各列之和可能大于总停顿周期。
3. **瓶颈编码给的是当下，累计计数给的是全程**。调试时先看 `bottleneck_o` 找当前卡点，跑完一段再看累计值算比例。
4. **除法留给软件**。硬件只给分子分母，避免为了一个性能数字在关键路径上放除法器。

## 两个坑

- **异步复位的下降沿要明确**。测试台里 `rst_n` 的初值写成 0，从 x 变到 0 在本机 Icarus 里不会触发 `negedge rst_n`，计数器停在全 x。要先拉高再拉低，给出一个真正的 1→0 沿。
- **自测任务的实参顺序要对**。初版把 `chk` 的形参写成 `msg` 在前、`cond` 在后，调用时却先传条件，结果消息打印成空白、判定也跟着乱掉（21 项里 13 项报 FAIL）。形参顺序改成 `cond` 在前才对得上。

## 已知简化

- 停顿事件由测试台直接给出，没有从各模块的真实状态里接出来。真实设计里这些信号要跨时钟域同步，还要处理计数溢出。
- 瓶颈优先级是固定的。真实性能分析更多靠跑完后看累计比例，固定优先级只适合做在线的粗略指示。
- 这里只数了四类事件。缓存缺失、TLB 缺失、功耗降频等都不在范围内。
