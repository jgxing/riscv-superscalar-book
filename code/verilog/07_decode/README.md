# 第 7 章 简化译码器代码

## 文件

- `decoder.v`：简化译码器。把几条代表性 RISC-V 指令翻译成 48 位的 uop，体现直译、拆分、融合三个思想。
- `tb_decode.v`：自测程序，30 项检查全过。

## uop 格式（48 位打包总线）

| 字段 | 位 | 含义 |
|---|---|---|
| op | [47:44] | 操作类型（ADD / SUB / LD / ST / LUI） |
| rd | [43:39] | 目的寄存器 |
| rs1 | [38:34] | 源寄存器 1 |
| rs2 | [33:29] | 源寄存器 2 |
| imm | [28:0] | 立即数（29 位） |

## 三个思想在代码里的落点

1. **直译**：ADDI、ADD、SUB、LUI、LD 各译成一条 uop（case 语句里各个分支）。
2. **拆分**：SD（双字存储）在 `opcode=0100011, funct3=011` 时，拆成两条 STORE.W，第二条立即数加 4，并置 `uop2_valid`。
3. **融合**：上一条是 LUI、当前是 ADDI、且目的寄存器一致时，合成一条带完整立即数的 ADD，置 `fused`。需要外部传入 `prev_inst`——这正是融合要在译码阶段做的原因。

## 一个关键点

这个译码器是**纯组合逻辑，没有时钟**。判断一个模块要不要时钟，看它要不要存储跨拍状态。译码器自己不存状态，融合要的历史由外部寄存器通过 `prev_valid`/`prev_inst` 提供。这点和第 4 章 FTQ、第 6 章指令缓冲队列（都带状态、需要时钟）形成对照。

## 已知简化

- LUI + ADDI 融合出的立即数是 32 位，但 uop 的 imm 字段只有 29 位，代码里做了高位截断。教学模型够用；真实处理器会把立即数字段做够宽或用别的方式携带。
- 指令识别只覆盖了少数几条代表性指令，不是完整 RISC-V 译码器。

## 运行

```bash
iverilog -g2012 -o sim.vvp decoder.v tb_decode.v
vvp sim.vvp
```

应看到 `ALL TESTS PASSED`，错误数为 0。测试覆盖：ADDI 直译、SUB 直译、LUI 直译、SD 拆分、LUI+ADDI 融合、融合条件不成立时不融合。
